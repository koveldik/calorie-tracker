## 1. Введение и назначение системы

### 1.1. Проблематика
Контроль рациона питания и соблюдение баланса макронутриентов (белков, жиров, углеводов — БЖУ) являются ключевыми факторами поддержания здорового образа жизни, контроля массы тела и достижения спортивных результатов. Ручной подсчет калорийности продуктов по таблицам неэффективен, подвержен ошибкам и отнимает много времени.

### 1.2. Цель проекта
Разработка и проектирование кроссплатформенной модульной информационной системы, позволяющей пользователям вести ежедневный дневник питания, рассчитывать энергетическую ценность съеденных порций в режиме реального времени, контролировать соблюдение персональной суточной нормы калорий, а также вести верифицированный справочник продуктов.

### 1.3. Основные задачи
1. Спроектировать реляционную модель базы данных с поддержкой разделения ролей пользователей и связей между бизнес-сущностями.
2. Реализовать клиент-серверную архитектуру на основе RESTful API.
3. Обеспечить полный жизненный цикл данных (CRUD-операции) для ключевых сущностей предметной области с разграничением прав доступа.
4. Контейнеризировать все компоненты системы (сервер приложений, СУБД, статический веб-сервер) с использованием Docker и Docker Compose.
5. Разработать интуитивно понятный пользовательский веб-интерфейс (SPA).

## 2. Архитектура информационной системы

Система построена по сервисно-ориентированной трехуровневой архитектуре (Three-Tier Architecture), где каждый уровень изолирован и функционирует в собственном независимом Docker-контейнере.

```
                      +-----------------------------+
                      |       Web Browser (UI)      |
                      +-----------------------------+
                                     |
                                     | HTTP (Port 3000)
                                     v
                      +-----------------------------+
                      |   Nginx Web Server Container|
                      |   (Статика SPA + Reverse    |
                      |    Proxy для /api/)         |
                      +-----------------------------+
                                     |
                                     | HTTP Proxy (Port 8000)
                                     v
                      +-----------------------------+
                      |   FastAPI Backend Container |
                      |   (Бизнес-логика, JWT Auth, |
                      |    Pydantic валидация, ORM) |
                      +-----------------------------+
                                     |
                                     | TCP (Port 5432)
                                     v
                      +-----------------------------+
                      | PostgreSQL Database Cont.   |
                      | (Хранилище данных, объемы)  |
                      +-----------------------------+
```

### 2.1. Стек используемых технологий
- **Backend (Серверная часть):**
  - **Python 3.11** + **FastAPI**: современный асинхронный фреймворк с автоматической генерацией OpenAPI/Swagger документации.
  - **SQLAlchemy 2.0**: Object-Relational Mapping (ORM) для типобезопасного взаимодействия с базой данных.
  - **Pydantic V2**: строгая валидация входящих и исходящих структур данных.
  - **Passlib & BCrypt**: криптографическое хэширование паролей пользователей с солью.
  - **Python-Jose**: генерация и верификация токенов авторизации стандарта JWT (JSON Web Token).
- **Database (База данных):**
  - **PostgreSQL 15**: надежная реляционная СУБД с поддержкой транзакций (ACID) и внешних ключей.
- **Frontend (Пользовательский интерфейс):**
  - **HTML5, CSS3, JavaScript (ES6+)**: легковесный Single Page Application (SPA) без тяжелых сторонних фреймворков.
  - **Nginx (Alpine)**: веб-сервер для отдачи фронтенда и реверс-проксирования API-запросов.
- **Инфраструктура:**
  - **Docker & Docker Compose**: стандартизированное развертывание мультиконтейнерной среды одной командой.

## 3. Бизнес-сущности и модель данных (2 CRUD)

В рамках требований лабораторной работы спроектированы и реализованы две ключевые взаимосвязанные бизнес-сущности предметной области, для которых реализован полноценный CRUD с проверкой прав доступа.

### 3.1. Сущность 1: Продукт питания (`FoodItem`)
Описывает единицу продовольственного продукта или готового блюда с указанием пищевой ценности на 100 грамм продукта.
- **Атрибуты:**
  - `id` (INTEGER, Primary Key) — уникальный идентификатор.
  - `name` (VARCHAR) — наименование продукта.
  - `calories` (FLOAT) — калорийность (ккал на 100 грамм).
  - `proteins` (FLOAT) — содержание белков (г на 100 грамм).
  - `fats` (FLOAT) — содержание жиров (г на 100 грамм).
  - `carbs` (FLOAT) — содержание углеводов (г на 100 грамм).
  - `category` (VARCHAR) — категорийная принадлежность (Мясо, Крупы, Овощи и т.д.).
  - `is_verified` (BOOLEAN) — признак верификации администратором.
  - `created_by_id` (INTEGER, Foreign Key) — ссылка на пользователя, создавшего продукт.
  - `created_at` (DATETIME) — временная метка добавления.

### 3.2. Сущность 2: Запись в дневнике питания (`MealEntry`)
Описывает факт употребления определенного продукта конкретным пользователем в рамках одного приема пищи.
- **Атрибуты:**
  - `id` (INTEGER, Primary Key) — уникальный идентификатор записи.
  - `user_id` (INTEGER, Foreign Key) — идентификатор пользователя (владельца записи).
  - `food_id` (INTEGER, Foreign Key) — идентификатор выбранного продукта из справочника.
  - `meal_type` (ENUM: `breakfast`, `lunch`, `dinner`, `snack`) — тип приема пищи.
  - `weight_grams` (FLOAT) — масса порции в граммах.
  - `note` (VARCHAR) — пользовательская текстовая заметка.
  - `consumed_at` (DATETIME) — дата и время приема пищи.
  - `created_at` (DATETIME) — время создания записи в системе.

### 3.3. Реализация CRUD-операций:
| Сущность | Create (Создание) | Read (Чтение) | Update (Редактирование) | Delete (Удаление) |
|---|---|---|---|---|
| **FoodItem** (Продукт) | `POST /api/foods/` — Клиент добавляет пользовательский продукт; Админ — верифицированный. | `GET /api/foods/` — Поиск по имени, фильтрация по категориям, просмотр детальной карточки. | `PUT /api/foods/{id}` — Клиент редактирует свои непроверенные; Админ редактирует любые. | `DELETE /api/foods/{id}` — Клиент удаляет свои; Админ удаляет любые (с валидацией ссылочной целостности). |
| **MealEntry** (Прием пищи) | `POST /api/meals/` — Добавление продукта и граммовки в свой дневник. | `GET /api/meals/` и `/summary` — Получение записей за дату, расчет БЖУ и прогресса калорий. | `PUT /api/meals/{id}` — Изменение граммовки, типа приема или продукта. | `DELETE /api/meals/{id}` — Удаление ошибочной записи из своего дневника. |

## 4. Разграничение прав доступа и ролевая модель

В системе реализована ролевая модель безопасности (RBAC) с двумя фиксированными ролями:

1. **Роль `<Client>` (Пользователь системы):**
   - Доступ к собственному личному кабинету и персональному дневнику питания.
   - Возможность задавать и корректировать индивидуальную суточную норму калорий.
   - Полноценное управление своими записями приемов пищи (CRUD дневника).
   - Поиск по общему справочнику продуктов.
   - Создание новых пользовательских продуктов питания и их редактирование до верификации администратором.
   - Запрет на доступ к чужим записям и админ-панели.

2. **Роль `<Admin>` (Администратор системы):**
   - Все полномочия обычного пользователя.
   - Модерация и верификация продуктов питания (установка флага `is_verified = true`).
   - Редактирование и удаление любых продуктов общего справочника.
   - Доступ к системной панели аудита (`/tab-admin`): просмотр истории активности и записей всех пользователей.

## 5. Инструкция по установке и локальному запуску

### 5.1. Требования
- Установленный **Docker** и плагин **Docker Compose** (Docker Desktop для macOS/Windows или docker-compose в Linux).

### 5.2. Запуск контейнеров
В корневой папке проекта (`calorie_tracker`) выполните команду:
```bash
docker-compose up --build -d
```

Команда автоматически:
1. Запустит СУБД PostgreSQL на порту `5432` и создаст базу данных `calorie_tracker`.
2. Соберет и запустит бэкенд FastAPI на порту `8000`, накатит схему БД и автоматически загрузит базовый справочник продуктов и тестовые учетные записи.
3. Соберет и запустит контейнер Nginx с фронтендом на порту `3000`.

### 5.3. Адреса сервисов
- **Веб-интерфейс приложения:** [http://localhost:3000](http://localhost:3000)
- **Интерактивная документация Swagger API:** [http://localhost:8000/docs](http://localhost:8000/docs)
- **Спецификация OpenAPI JSON:** [http://localhost:8000/openapi.json](http://localhost:8000/openapi.json)
